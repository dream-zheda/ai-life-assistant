```

pnpm worker:once  → {"job":null,"remindersCreated":0,"dispatch":{"sent":0,...}}
```

集成覆盖：并发领取无重复、租约过期可重领、退避重试、提醒去重、窗口内发送、
窗口外标 `FALLBACK_REQUIRED` 且**不发送**、计划被替代后旧提醒作废、未绑定通道时降级。

**过程中抓到一个会让提醒早 8 小时的 bug：**

Prisma 的 `DateTime` 存成无时区的 `timestamp`（UTC），但 `$queryRaw` 的 `Date` 参数被绑定成
`timestamptz`。PG 比较时按会话时区（+08）换算，于是「60 秒后」的任务被当成「8 小时前」，
直接可领取——放到生产就是**提醒提前 8 小时触发，且没有任何报错**。

修法是原生 SQL 里显式 `AT TIME ZONE 'UTC'`。第一版修法还把整段表达式拼进了参数（变成
`timestamp <= text` 报错），正确写法是参数只放值、转换写在 SQL 文本里。详见 ADR-005。

同时把领取语句从 `WHERE id = (SELECT ...)` 改成 PostgreSQL 官方推荐的
`UPDATE ... FROM (SELECT ... FOR UPDATE SKIP LOCKED)`。

### 10. 重复约束展开与跨零点修正

| 产出 | 说明 |
| --- | --- |
| `packages/domain/src/planning/repeat.ts` | 「每天/工作日/周末/指定星期」→ 多条 weekly 约束的纯函数展开 |
| `FixedConstraint.groupId` | 展开出的多条共享同一个组，可整组删除 |
| `apps/web/src/server/constraints.ts` | 写库、整组删除、按组合并展示 |
| `fixedSlotIntervalsOnDay` | **同时返回当天生效的与前一天溢出的两段区间** |

**这轮最有价值的一件事：测试否掉了 ADR-003 自己提出的方案。**

ADR-003 原方案是"每天展开成 7 条就够了"。集成测试直接打脸：

```
expected 480, received 60
```

原因是 `fixedSlotIntervalOnDay` 只回答「**这条规则**在当天是否生效」，
周一的规则在周二返回 `null`——周二凌晨 00:00–07:00 仍然漏算。

修正需要**两条措施同时成立**：

| 措施 | 解决什么 |
| --- | --- |
| 展开成 7 条 | 让每个夜晚都有一条规则声明 |
| 同时看前一天 | 让前一条规则的尾巴进入当天的占用 |

只做第一条 = 每晚只算 60 分钟；只做第二条 = 没有周一的规则，拿不到尾巴。

**实测：**

```
pnpm test      → 85 个（新增 12：展开规则 10 + 跨零点溢出 2）
pnpm test:int  → 20 个（新增 5：约束组展开与删除）
  - 7 条展开后当天占用 = 480 分钟
  - 对照组：只留周二一条 = 60 分钟
```

| --- | --- |

**为什么现在才做：** 规划书 §3 早就要求「免打扰、频率限制、暂停」，但一直缺一个
**用户能设置的地方**——字段存在但碰不到，等于没有。

**三个实现细节：**

1. **暂停优先于一切。** 判断顺序是 暂停 → 免打扰 → 每日上限。用户按了暂停之后，
   即使还在白天、没到上限，也不该有任何推送。
2. **免打扰必须支持跨零点。** 23:00–07:00 是最常见的设置，
   按 `start < end` 的朴素比较会被判成"永不生效"。
3. **被抑制的提醒要留痕。** 记成 `blocked` + 原因码（`paused` / `quiet_hours` / `daily_limit`），
   不是静默丢掉——否则排查"为什么没收到"时无从下手。

**实测：**


改成三段串联，并把 web 的集成测试纳入：

```
pnpm typecheck = tsc(packages) && tsc(apps/web) && tsc(apps/worker)
```

这不是"防御性编程"，是上一轮就在这个盲区里踩过一次：settings 页面的问题是被 `next build` 发现的，
而 `next build` 只在有人记得跑时才跑。

**② 合规边界**

新增 `docs/compliance.md` + 用户可见的 `/privacy` 页。要点：

| 主张 | 文档/页面里的写法 |
| --- | --- |
| 会发给模型服务商 | 明说，不藏在细则里 |
| 没有端到端加密 | 明说"管理员理论上能看到明文" |

比没有隐私文案更糟。

**实测：**

### 17. 约束组编辑

| 产出 | 说明 |
| --- | --- |
| `updateConstraintGroup` | 事务内替换展开行，**保留 groupId 与 createdAt** |
| `inferRepeat` | 从星期集合反推「每天/工作日/周末/指定某天」 |
| `/constraints/[groupId]` | 编辑页，表单回填；不存在或非本人 → 404 |

**为什么不能"删了重建"：** 那样 `createdAt` 每次编辑都会归零，
"这条作息是什么时候设的"就永远查不到。现在保留最早那条的时间戳。

**一个刻意的拒绝：** 如果一组的星期集合不属于任何预设（例如手工造的数据），
`inferRepeat` 返回 `null`，页面显示"暂不支持编辑"而不是猜一个最接近的预设——
猜错会静默改掉用户的作息。

**实测：**

```
pnpm test:int  → 64 个（新增 5：反推预设 3 + 编辑 2）
真实 HTTP：
  GET /constraints/<自己的分组>   → 200，星期回填为「周二」
  GET /constraints/<不存在的分组> → 404
```

**过程中的一个教训：** 第一次验证时页面返回 404，原因是 `next start` 用的是**上一轮的构建产物**——
新加的页面没构建。`next start` 永远跑 `.next` 里的东西，改完页面必须重新 `build`。

### 20. 计划生效（补上断掉的主链路）

| 产出 | 说明 |
| --- | --- |
| `apps/web/src/server/plan-activation.ts` | DRAFT → ACTIVE，事务内先撤旧再启新 |
| `apps/web/src/app/actions.ts` | `activatePlanAction` |
| `/today` | DRAFT 计划显示「这份计划还没有生效」+「采纳这份计划」 |

**这轮发现的是一处"拼起来才断"的链路：**

| 模块 | 单独看 | 合起来 |
| --- | --- | --- |
| 规划生成 | 写入 DRAFT ✅ | |
| `/today` 展示 | 显示最新版本 ✅ | |
| worker 提醒 | 只处理 ACTIVE ✅ | **计划永远是 DRAFT → 永远不会提醒** |

每一层都通过了自己的测试，但用户点「生成计划」之后**永远收不到任何提醒**。

**三个实现要点：**

1. **先撤旧、再启新。** 部分唯一索引要求同一天只有一个 ACTIVE，顺序反了会立刻撞索引。
2. **采纳前丢弃已结束的条目。** 计划是异步生成的，用户可能隔一阵才点采纳；
   一条都不剩时**拒绝采纳**并提示重新生成。
3. **只接受 DRAFT。** 已替代的版本不允许再被采纳，否则会用旧版本覆盖新版本。

**实测：**

```
pnpm test:int  → 70 个（新增 6：采纳）
真实 HTTP      → /today 对 DRAFT 计划显示「采纳这份计划」表单
```

详见 ADR-008。

### 22. 条目上限与 README

| 产出 | 说明 |
| --- | --- |
| `TOO_MANY_ITEMS` 校验 | 一天最多 N 项，N 由可用时间在 6–24 之间推导 |

### 23. 个人号协议登录（通道适配器）

| 产出 | 说明 |
| --- | --- |
| `packages/channels/src/policies.ts` | 从 index 抽出策略（避免与适配器循环依赖） |
| `packages/channels/src/wechat-bridge.ts` | 桥接适配器：HMAC、错误分类、限速、入站解析 |
| `packages/channels/src/rate-limit.ts` | 令牌桶（本地限速，降低封号画像） |
| 迁移 `wechat_protocol_session` | `ChannelKind` 新增值 + 会话状态字段 |

**产品决策（由所有者拍板）：** 用户自备微信号，扫码登录到桥接服务，AI 以好友身份发消息。
这条路**没有推送窗口**，但**违反微信规范 1.2.6**——代价与收敛措施见 ADR-009。

**三条自我约束（写进代码而不是文档）：**

1. **绝不存储密码**，只存 `bridgeSessionId` 引用；登录由桥接服务扫码完成。
2. **本地令牌桶限速**（默认 6 条/分钟）。突发高频是最典型的封号画像，
   等服务端 429 已经晚了。
3. **网络异常记 `unknown` 而不是 `failed`。** 我们不知道消息有没有出去，
   当失败重试会重复打扰用户。

**会话状态建模**：`PENDING_SCAN` / `ACTIVE` / `EXPIRED` / `DISCONNECTED` / `BANNED`。
缺了它，系统无法区分「用户没回消息」和「账号已经死了」——后者是这条路的常态。

**实测：**

```
pnpm test      → 138 个（新增 14：适配器与限速）
pnpm test:int  → 70 个
pnpm e2e       → 17 / 17
db:rehearse    → 5 个迁移（新增 1 个）仍零漂移
```

**没有验证的：** 桥接服务能否稳定登录、封号概率、微信是否检测——都需要真账号与真环境。

### 26. 页面上填模型 API Key

| 产出 | 说明 |

**用户反馈：**「不希望填 api 页面和计划放在一起」「链接完之后这个页面也没有改变」。

**改动：**

| 变化 | 说明 |
| --- | --- |
| 新增 `/setup/model` | 只干一件事：填 Key。保存后顶部出现绿色「✅ 已接入 … · Key ••••1234」 |
| `/onboarding` 去掉表单 | 只留一行状态 + 「去填 API Key」按钮，回到「填情况」本职 |
| 注册后跳转 | `/sign-up` → **`/setup/model`**（先配模型再谈生成） |
| 按钮文案 | 「测试连接（不会保存）」——之前点测试不保存，用户以为页面坏了 |
| `/today` 顶部卡片 | 未接入模型时直达 `/setup/model` |

**关于"页面没变化"：** 有一半是文案误导——「测试连接」本来就不写库。
现在按钮上直接写明，并且成功保存后有整块状态卡，不再是细微变化。

**实测（临时邀请账号，11 项全过）：**

```
OK  模型页有 Key 输入框
OK  未接入时提示明显
OK  按钮写明测试不保存
OK  保存后显示已接入 / 末四位 / 「换一个」/ 不再是未接入
OK  引导页不再含 API Key 与 Base URL 输入框
OK  引导页有去模型页的链接
```

### 29. 模型错误的可读性

**用户反馈：**「key被拒绝」——只有这一句，看不出问题在哪。

**根因：** `upstreamError` 把服务商响应体放在 `AppError.details.body` 里，而
`testModelConfig` 只读了 `error.message`（内容是 `openai 返回 HTTP 401`），
**把最有价值的服务商原文丢掉了**。

**改动：**

| 变化 | 效果 |
| --- | --- |
| 读取 `details.body` 并解析 `error.message` | 错误里带出服务商原话 |
| 错误信息带 endpoint 与模型名 | 一眼看出 Key 被发到了哪家 |
| 单独识别 402 / 余额不足 | 不再把欠费说成"Key 被拒" |
| 页面显示「请求会发到 …/chat/completions」 | 填之前就知道发往何处 |
| 页面加「常见原因」折叠说明 | 4 条高频错误 |

**实测（假服务商返回 401/402，6 项全过）：**

```
Key 被拒绝（401/403）。请求发往 http://…/v1/chat/completions，模型 gpt-4o-mini。
请确认：①Key 与所选服务商匹配… 服务商原文：Incorrect API key provided: sk-xxxx…

服务商说余额/额度不足（不是 Key 错误）。… 服务商原文：Insufficient Balance
```

### 30. 模型页收小 + 拦住「把网址当 Key」

**用户反馈：**「把换 api 的页面搞小一点就留一个按钮」，
以及一条真实报错：`Your api key: ****.com is invalid`——**填进去的是网址，不是 Key**。

**改动：**

| 变化 | 说明 |
| --- | --- |
| 已配置时 | 只显示一行 `DeepSeek · deepseek-chat · Key ••••7890` + **一个**「更换 API Key」按钮（`<details>` 展开表单） |
| 未配置时 | 直接显示表单（没有 Key 时藏起来等于没得填） |
| 去掉冗长说明 | 常见原因块、endpoint 提示都删了，错误信息本身已经够用 |
| `looksLikeWrongSecret` | 网址/邮箱/含空格 → 本地直接拒绝，不发请求、不写库 |

**为什么加这道校验：** 服务商只回一句 `****.com is invalid`，
用户看不出是自己填错了框，我们也看不出——**两边都在猜**。

**实测：**

```
模型配置集成测试 → 13 个全过（含新增 4 个网址识别用例）
页面两种状态     → 已配置：一行 + 一个按钮；未配置：表单
```

### 31. 修一个会误导人的报错：空计划 ≠ 安排过期

**用户反馈：**「采纳里的安排已经过去了似乎有 bug」。

**查库结果：** 该账号有 2 个 `DRAFT` 计划，**各 0 条安排、0 条提醒**——
生成时还没接入模型，mock 返回的是空计划。

**根因：** `activatePlanVersion` 把两种情况塞进同一个 `empty` 分支：
- 计划一条安排都没有（没配模型）
- 安排全都已经结束（生成太久才采纳）

于是点「采纳」时统一提示「这份计划里的安排都已经过去了」——**把"没有安排"说成了"过期"**。

**改动：**

| 变化 | 说明 |
| --- | --- |
| 拆成 `empty` 与 `expired` | 空计划提示"先去接入模型"；过期提示"重新生成" |
| `/today` 空计划卡片 | 不再显示「采纳」，改成「去接入模型」+「重新生成」 |
| 测试 | 新增"零条目 → empty"用例 |

**实测：**

```
采纳集成测试 → 7 个全过
页面验证     → 6 / 6（显示"这份计划是空的"，且不再出现"采纳"与"都已经过去"）
```
