## 1. 最高优先级：多用户 × 微信主动提醒，是资质问题而不是技术问题

规划书 §12 要求"必须先做真实验证"，方向正确，但**没有给出通道的能力矩阵**。结果是：接手 agent 可能写到 P4 才发现所选通道根本不支持"给任意注册用户主动发消息"。

### 1.1 通道能力矩阵

| 通道 | 能否给任意注册用户主动发消息 | 前置资质 | 使用体验代价 | 核验状态 |
| --- | --- | --- | --- | --- |
| **企业微信自建应用** | ❌ 仅限**企业通讯录成员** | 注册企业微信（个人可注册） | 用户必须被拉进你的"企业"，在微信侧需装微信插件才能收到；未认证**默认 200 人上限** | 上限已核验（[官方 FAQ](https://kf.qq.com/touch/apifaq/160415qIjUZr160415JvAfYr.html?platform=14)） |
| **认证服务号（公众号）** | ✅ 支持模板消息/客服消息 | **企业主体 + 微信认证（约 300 元/年）** | 用户需关注公众号；模板消息有格式与字段限制 | 待核验 |
| 个人订阅号 | ❌ 无主动推送接口 | — | 只能被动回复 | 待核验 |
| 公众号测试号 | 仅限少量关注者 | 无 | 不稳定，不适合生产 | 待核验 |
| 小程序订阅消息 | ⚠️ 需用户**每次点击订阅** | 小程序主体 | 需要小程序前端配合，不是纯后端通道 | 待核验 |
| **扫码登录个人微信** | ✅ | 每个用户一个微信号 | **违反微信规范，封号风险随用户数放大** | 定性明确 |
| Server酱 / PushPlus | ❌ 只能推给绑定者本人 | — | 单用户可用，平台化不可用 | 定性明确 |

### 1.2 由此得出的路线判断

| 第一版形态 | 可用通道 | 结论 |
| --- | --- | --- |
| **邀请制 + 3~10 个熟人** | 企业微信自建应用 | ✅ **可行**。规划书 §2 选"邀请注册"恰好救了它。但必须在文档写明"用户需加入企业通讯录、未认证上限 200 人"这一体验代价 |
| 公开注册 / 任意互联网用户 | 认证服务号 | ⚠️ **必须提前准备企业主体 + 认证**。个体户营业执照一般可作为企业主体完成认证，但这是**流程性工作（数周）**，不是写代码能解决的 |
| 追求原生微信聊天体验 | 扫码协议 | ❌ 不建议平台化。风险与用户数成正比 |

### 1.3 建议动作

1. 把 §1.1 矩阵整体并入规划书 §12 开头，作为"通道选型前置结论"。
2. 在 §2 决策表新增一行：**「第一版仅限邀请制、不开放公开注册」** —— 这是降低合规与资质成本的关键主动选择，应显式写下而不是默认。
3. P0 的交付物从"微信实测"改为两件事：**（a）资质清单**（是否需要营业执照、是否需要认证、预算与周期）；**（b）通道实测记录**。资质在前，因为资质决定通道。

## 2. 与既有需求相比的范围变化（需你确认，非错误）

| 项 | 早期判断 | v1.0 规划书 | 影响 |
| --- | --- | --- | --- |
| 用户模型 | 单用户，仅预留 `user_id` | **第一版即多用户** + 邀请 + 管理后台 | 认证、隔离、限流、额度、审计全部从"可选"变成"必需"，工作量约 ×2.5 |
| 核心价值 | 提醒"今天要做的事" | **AI 生成并持续调整生活规划** | 产品重心从"提醒"移到"规划"；提醒质量取决于规划质量 |
| 待办来源 | 手动录入 + 聊天提取 | AI 生成，用户补约束 | 手动录入降级为"约束输入"，产品逻辑更自洽 |
| 前端定位 | 配置台 | 9 个页面 | 前端工作量显著上升 |

规划书把这些变化记录为"已确认"，我按已确认处理。但建议补一句限定：**"第一版多用户是为了验证数据隔离，不代表要对外开放注册"**，否则容易被后续 agent 理解成要做公开产品。

## 3. 缺失的四个章节（建议补进规划书）

### 3.1 合规边界（完全缺失）

- **PIPL**：面向他人收集个人信息需"告知—同意"，至少要有一个最小隐私说明页与同意记录。
- **生成式 AI 服务管理**（境内）：面向公众提供生成式 AI 服务可能涉及算法/模型备案与内容安全责任。**仅自己与少数熟人内部使用通常不触发**，但公开注册就会碰。
- 建议新增一节「合规边界」，明确写：第一版限邀请制、不公开注册、不面向未成年人、不提供医疗/法律/金融等专业建议。

### 3.2 成本模型（只有"额度"概念，没有数字）

§13 写了限流，§9 有"用量记录"，但没有任何预算估算。缺了它，"额度"没有依据。

- 需要估算：每用户每天 = 1 次周规划 + 1 次日计划 + N 轮聊天 ≈ 多少 token。
- 据此定默认额度（如每人每天 X 次生成、Y 千 token），再定超限行为（拒绝 / 降级到便宜模型 / 提示）。
- 结论写进 §9 或新开一节。

### 3.3 可观测性（仅 `/health`，不足以证明系统在正常工作）

§15 提到"健康检查还应能观察 worker 是否持续工作"，但没定义怎么做。建议明确三个指标 + 一个告警：

| 指标 | 为什么 |
| --- | --- |
| 提醒成功率（发送次数 / 应发送次数） | 唯一能证明产品在履约的指标 |
| 任务积压深度（待执行任务数 / 最老任务年龄） | worker 静默死亡时，网页仍然 200 |
| 模型调用失败率与 P95 延迟 | 规划生成是异步的，失败必须可见 |

**告警通道不能用微信**（通道挂了就收不到告警），要用邮件或第三方。

### 3.4 「反馈 → 调整」的触发规则（全篇最薄的一环）

这是我认为**最需要补的一节**。§5 说"根据完成情况和临时变化调整规划"，§12 讲提醒机制，但**没有任何地方定义"什么条件下应该重排"**：

- 用户在微信说"今天下午要加班" → **自动重排剩余时段，还是先问一句？**
- 连续 3 天标记未完成 → 降低强度、还是提示用户修改目标？
- 已完成 60% 的任务被新计划覆盖 → 保留还是丢弃？（§5 只说"保留已完成记录"，没说条目级行为）

规则不定，AI 每天的"重排/不重排"就是随机的，产品体验不可复现。建议新增 §5.x「调整触发规则表」：

| 触发条件 | 系统动作 | 是否需用户确认 |
| --- | --- | --- |
| 用户消息含明确时间冲突 | 生成修订草稿 | 确认模式下需确认 |
| 当日 ≥2 项未完成 | 次日降低负荷 10~20% | 否，但需告知 |
| 用户手动暂停提醒 | 只停发送，不动计划 | — |
| 连续 7 天完成率 < 30% | 建议重构目标 | **必须**确认 |

## 4. 逐条可落地性缺陷

| 原文位置 | 问题 | 建议 |
| --- | --- | --- |
| §8「不引入 Redis 也可以完成任务队列」 | 只说了"事务和锁领取"，没给实现。这在 Prisma 里不写原生 SQL 做不到 | 明确用 `SELECT ... FOR UPDATE SKIP LOCKED`（Prisma 需 `$queryRaw`），或直接引入 `pg-boss`；否则"锁租约"落不了地 |
| §10 `generateStructured(): Promise<unknown>` | 返回 `unknown` 等于把校验责任丢了，调用方必然写出 `as` 强转 | 改成泛型 `generateStructured<T>(schema: ZodType<T>, input): Promise<T>`，在适配器内部校验 + 有限重试 |
| §10 超时/长度限制 | 只说"应包含"，没有默认值。各 SDK 默认行为不同，会导致同一 prompt 在两家服务商表现不一致 | 给出默认值（如超时 60s、输出上限 4096 token、重试 2 次） |
| §5「不安排到已经过去的时段」 | 生成有耗时，存在竞态：23:50 发起生成，模型返回时 23:45 那个条目已过期 | 在**生效前**用当前时间二次过滤，丢弃已过期条目并在 `assumptions` 里说明 |
| §11 接口表 | §3 承诺了"个人数据导出、删除入口"，但 §11 没有对应端点 | 补 `GET /api/me/export`、`DELETE /api/me` |
| §11 接口表 | 邀请功能无端点 | 补 `POST /api/admin/invites`、`GET /api/admin/invites`、`DELETE /api/admin/invites/:id` |
| §12 | 只定义了**发送机制**，没定义**提醒内容**：一条微信消息多长？分条还是合并？能否让用户直接回"完成"？ | 新增「消息形态」小节，给出模板与上限（建议单条 ≤ 300 字，超长拆分或改摘要 + 网页链接） |
| §14 测试表 | 缺时区与跨日边界 | 补：23:59 生成计划、跨时区用户、免打扰跨越零点 |
| §16 第 1 条 | 要求读 `AGENTS.md`，但当前工作区**不存在**该文件 | 改为"若存在则读"，或由接手方首先创建 |
| 全文 | 只说"锁定兼容版本"，没有锁定策略 | 明确：初始化时锁次版本号，提交 lockfile，CI 用 `--frozen-lockfile` |

## 5. 值得保留、后续不要被"优化"掉的部分

这几点是全篇质量上限所在：

1. **§12 的提醒生命周期顺序**：计划生效事务 → 保存新版本 → 替代旧版本 → **取消未发送的旧提醒** → 创建新提醒 → 提交。这是绝大多数同类项目会写错的地方（新计划建了提醒、旧计划提醒没撤）。
2. **§10「模型调用在数据库事务之外执行」** —— 长事务占锁是多用户系统最常见的性能事故。
3. **§2 的三态标注**（已确认 / 技术建议 / 待验证），让接手者不会把"建议"当"结论"。
4. **§14 的验收表以越权、并发、崩溃恢复为主**，而不是"页面能打开"。
5. **"通道接受 ≠ 用户收到"** —— 明确拒绝虚假送达承诺，这个克制很专业。
6. **§13「不能声称端到端加密」** —— 主动划清能力边界，避免过度承诺。
