## 1. 项目目标与用户真实意图

构建一个支持多用户的 AI 个人生活助手平台。

用户通过网页提供个人背景、生活现状、目标、偏好和现实约束。系统调用用户选择的大模型 API，生成生活规划，通过微信提醒并与用户交流，再根据完成情况和临时变化调整规划。

核心使用流程：

```text
用户注册或受邀加入
        ↓
网页录入个人情况、目标、偏好和现实约束
        ↓
AI 整理信息，必要时追问
        ↓
AI 生成生活规划，用户可以调整或接受
        ↓
系统按生效计划发送微信提醒
        ↓
用户通过微信或网页反馈
        ↓
系统记录进展，AI 提出或执行授权范围内的调整
```

用户已经明确：

- 希望助手规划整体日常生活，覆盖学习、工作、健康、娱乐等领域。
- 英语学习与游戏时间冲突只是示例，产品不应围绕英语单独设计。
- 用户主要录入"自己的情况"，具体安排由 AI 生成。
- 支持官方大模型 API，且不局限于 DeepSeek。
- 支持多个用户登录，各自拥有个人助手。
- 希望通过微信接收提醒，也希望在微信里直接对话。
- 计划部署到常驻云服务器。
- 接受按"新建业务项目、复用成熟组件"的方向继续规划。

用户可以补充固定课程、已有约定、截止日期等现实信息。系统不能假定自己能够自动知道这些事实。

## 4. 页面与交互设计

| 页面 | 主要内容与操作 |
| --- | --- |
| 登录与加入 | 登录、接受邀请、建立账号 |
| 首次了解 | 简要背景、主要目标、可用时间、已有约束、规划偏好 |
| 今日 | 当前计划、下一步行动、完成反馈、提醒状态、调整计划 |
| 我的情况 | 档案、固定安排、偏好、助手记忆 |
| 我的目标 | 新增或描述目标、优先级、进度、暂停或结束 |
| 计划记录 | 每日与每周计划、生成依据、调整历史、完成情况 |
| 和助手讨论 | 补充信息、讨论取舍、请求调整 |
| 设置 | 默认模型、微信绑定、时区、提醒、隐私与数据管理 |
| 管理后台 | 邀请、账号、模型服务、额度、运行异常 |

首次录入不应成为长问卷。建议先获取：

1. 当前处于什么生活阶段。
2. 最希望改善或推进的几件事。
3. 通常几点起床、睡觉，哪些时段被占用。
4. 已有约定与明确截止事项。
5. 希望计划宽松还是紧凑。

允许用户输入：

> 我现在是大学生，白天有课，晚上容易打游戏，想提高英语和规律运动，希望保留娱乐时间。

AI 整理为档案草稿，并区分：

- 用户明确说过的信息。
- AI 推测、需要确认的信息。
- 仍缺少但影响规划的信息。

用户可以逐步补充，未知字段保持未知。

"今日"页面至少呈现：

```text
日期与当前计划状态
今天最重要的几件事
当前或下一项行动
今天的时间安排
完成／部分完成／调整／跳过
需要用户确认的问题
一句话补充变化的输入框
```

生成中、生成失败、尚未确认、无计划和通道未绑定，都应有明确状态与后续操作。

## 5. 生活规划的业务规则

AI 生成规划前，系统汇总：

- 当前日期、用户时区与可用时间。
- 个人档案和已确认偏好。
- 正在推进的目标。
- 固定安排与截止事项。
- 当前计划和实际执行进度。
- 用户近期明确反馈的状态。

规划过程：

1. 占用固定约束对应的时段。
2. 根据目标、截止时间和用户偏好决定优先级。
3. 将目标拆成具体可执行行动。
4. 分配时间，并预留休息、娱乐与缓冲。
5. 检查时间冲突和总量。
6. 展示计划、重要取舍和需要确认的假设。

以下规则必须实现：

- 不改变用户已有约定的真实日期。
- 不安排到已经过去的时段。
- 不将同一可执行任务重复安排在冲突时段。
- 任务超出可用时间时，明确提出延期或减量建议。
- 允许安排娱乐、社交和休息。
- 不把没有反馈解释为没有完成。
- 不把点击"开始"解释为完成。
- 部分完成时保留实际进度。
- 单次状态差，不自动修改长期目标。
- 新计划保留已完成记录，并处理正在进行的行动。

AI 可以为目标生成新行动，例如给英语目标提出练习建议；必须标明这是 AI 建议。它不能把编造的课程、约定、教材或截止日期当成用户事实。

计划与执行状态分开管理：

```text
计划版本：草稿 → 生效 → 被新版本替代
行动执行：待进行 → 进行中 → 部分完成／完成／跳过／取消
```

延期通常意味着改变行动的安排时间，应保留对应记录与变更原因。

## 6. 自动规划和用户控制

建议保留两个设置：

| 设置 | 行为 |
| --- | --- |
| 确认模式 | 新计划和重要调整由用户接受后生效 |
| 自动模式 | 在用户授权的时段、目标和规则范围内自动生效 |

建议第一份计划必须展示给用户检查。后续是否自动生成和生效，由用户选择。

用户应能：

- 固定某项行动或某段时间。
- 暂停某个目标。
- 暂停提醒，但保留计划。
- 查看本次调整影响了哪些事项。
- 撤销最近一次符合条件的调整。

撤销也要检查当前进度：已经执行或完成的行动不能被无条件回滚为未开始。

## 7. GitHub 复用策略

默认不整仓搬运现有机器人或 AI 平台作为业务底座。优先复用依赖库；确有需要时使用独立桥接服务或插件。

| 需求 | 建议方式 |
| --- | --- |
| 登录认证 | 使用成熟认证库 |
| 数据库与迁移 | 使用成熟 ORM 和迁移工具 |
| 多模型请求 | 官方 SDK 或可靠的服务商适配层 |
| 微信接入 | 根据实测选择直接接入、独立桥接服务或已有插件 |
| 档案、目标、计划与进度 | 自建业务代码 |
| 计划版本与提醒一致性 | 自建并重点测试 |
| 页面 | 按本产品设计，使用常规 UI 组件库 |

候选项目：

- [AstrBot](https://github.com/AstrBotDevs/AstrBot)：核验消息适配和插件扩展价值。
- [chatgpt-on-wechat](https://github.com/zhayujie/chatgpt-on-wechat)：核验当前微信接入方式。
- [Dify](https://github.com/langgenius/dify)：可用于验证提示词和工作流，是否作为运行依赖另行评估。
- [WeClaws](https://github.com/yokingma/weclaws)：参考多用户托管、状态持久化和外部运行契约。

以上仓库的最新代码与许可证尚未核验，不保证符合需求。

实际核验时记录：

| 检查项 | 所需证据 |
| --- | --- |
| 维护状态 | 检查日期、提交版本、近期发布与相关问题 |
| 许可证 | 代码使用、修改、分发及依赖条款 |
| 多用户 | 是否支持终端用户身份与数据隔离 |
| 接入方式 | 有无稳定 API、插件接口或消息契约 |
| 微信能力 | 多用户绑定、接收消息、主动发送的实测结果 |
| 持久化 | 重启后身份与待处理任务是否恢复 |
| 部署成本 | 进程、内存、数据库及额外服务要求 |

只有在项目高度匹配、扩展接口稳定、许可证合适且升级成本可控时，才考虑 fork。

若使用独立桥接服务，业务数据库仍保存用户、目标、计划和提醒的最终状态。桥接服务不另建一套生活规划数据。

以下为逻辑实体，最终字段在数据库设计时完善。

| 实体 | 关键内容 |
| --- | --- |
| 用户与认证数据 | 账号、会话、角色、停用状态；优先使用认证库结构 |

| 行动任务 | 具体动作、对应目标、预计时长、来源 |
| 计划版本 | 规划范围、版本、状态、生成依据、模型调用关联 |

| 进度事件 | 完成比例、实际耗时、反馈、发生时间 |
| 记忆 | 内容、来源、确认状态、有效期、敏感性标记 |

| 用量记录 | 模型、请求、token、费用估算 |
| 审计记录 | 关键操作、操作者、对象与结果 |

必须落实的数据库约束：

- 个人业务数据包含 `user_id`。
- 引用目标、任务和计划时，保证关联对象属于同一用户；可使用复合唯一键与外键。
- 一个用户同一规划周期只能有一个生效版本，第一版日计划按用户当地日期管理。
- 回调去重键包含通道实例与外部事件标识，不能仅用一个未限定范围的消息 ID。
- 同一计划条目的同一提醒有唯一幂等键。
- 档案和计划具有版本号，用于检测并发修改。
- 绝对时间存储为带时区时间戳；用户时区保存为 IANA 标识，例如 `Asia/Shanghai`。
- "每天 22:00 免打扰"等本地时间规则保存本地时间与时区，不能只转成固定 UTC 时间。

第一版所有用户默认北京时间也可以，但不能在代码中写死只支持这一时区。

## 10. 多模型接口与 AI 输出契约

统一接口用于隐藏不同模型服务商的请求差异。下面是参考契约，不代表已经实现：

```ts
type ModelRef = {
  providerId: string;
  modelId: string;
};

interface LlmAdapter {
  generateText(input: TextRequest): Promise<TextResult>;

  generateStructured(
    input: StructuredRequest
  ): Promise<unknown>;
}
```

`StructuredRequest` 应包含消息、输出结构要求、超时和输出长度限制。返回值必须经业务 Schema 校验后才能使用。

不能假定所有服务商都支持相同协议。可以复用兼容接口，同时为不同原生协议提供适配器。

首版实际接入 DeepSeek 和另一家可用的官方服务商。第二家由用户凭据及部署环境决定，其余显示为未配置，不能宣称已验证。

计划输出参考：

```ts
type ProposedPlan = {
  localDate: string;
  timezone: string;

  items: Array<{
    existingTaskId?: string;
    goalId?: string;
    title: string;
    startAt: string;
    endAt: string;
    estimatedMinutes: number;
    reason: string;
  }>;

  assumptions: string[];
  unresolvedQuestions: string[];
};
```

系统根据调用上下文确定用户身份、计划版本和权限，不能信任模型输出的这些字段。

生成流程：

```text
读取当前用户的数据快照与版本
→ 计算日期、可用时段和硬约束
→ 拼接必要上下文
→ 调用模型
→ 校验结构
→ 校验时间、归属、引用与业务规则
→ 检查数据版本是否仍然有效
→ 保存草稿或按授权生效
```

补充要求：

- 模型调用在数据库事务之外执行，避免长时间占锁。
- 资料在生成期间发生变化时，不能覆盖新状态。
- 无效输出允许有限次数修复；仍失败则保留原计划并报告原因。
- 相对日期以消息发生时间和用户时区为依据；"下周找时间"等有歧义表达先澄清。
- 用户输入与系统规则分开组织，模型没有直接执行任意 SQL 或系统命令的能力。
- 服务商之间自动切换涉及数据发送对象变化，应由用户设置允许。
- 调用前检查额度，并为并发请求预留用量预算；结束后按实际用量结算。

## 11. API 与业务服务约定

以下是建议接口，路径可微调，但语义应保持一致。

| 接口 | 用途 |
| --- | --- |
| `/api/auth/*` | 认证库管理的登录、会话与退出 |
| `GET/PATCH /api/me/profile` | 查看或修改个人档案 |
| `GET/PATCH /api/me/settings` | 个人设置 |
| `GET/POST/PATCH /api/constraints` | 固定约束 |
| `GET/POST/PATCH /api/goals` | 目标管理 |
| `POST /api/plans/generate` | 发起异步规划 |
| `GET /api/jobs/:id` | 查询当前用户的任务状态 |
| `GET /api/plans/today` | 获取今日生效计划 |
| `GET /api/plans/:id` | 查看指定计划及版本信息 |
| `POST /api/plans/:id/activate` | 接受计划并更新提醒 |
| `POST /api/plans/:id/revise` | 请求调整计划 |
| `POST /api/tasks/:id/progress` | 提交完成或部分完成反馈 |
| `POST /api/conversations/:id/messages` | 网页聊天 |
| `GET/PATCH/DELETE /api/memories/:id` | 管理个人记忆 |
| `GET /api/models` | 查看当前用户可用模型 |
| `POST /api/channel-bindings/start` | 开始外部身份绑定 |
| `/api/webhooks/:channel/:instance` | 通道验证与消息回调 |
| `GET /api/notifications` | 查看自己的提醒记录 |
| `/api/admin/*` | 管理员接口 |
| `/health/live`、`/health/ready` | 存活与依赖可用性检查 |

规则：

- 个人接口从服务端会话获取用户身份。
- 访问任意对象 ID 时都检查归属。
- 计划生成返回 `202 + jobId`，客户端查询或订阅任务状态。
- 计划变更带预期版本，版本不匹配返回冲突。
- 关键写操作接受幂等键。
- JSON 错误包含稳定的错误码和可展示说明。
- 用户接口、管理员接口和 webhook 分别认证。

业务服务示例：

```ts
interface PlanningService {
  requestGeneration(
    actor: UserContext,
    input: GeneratePlanInput
  ): Promise<JobRef>;

  activate(
    actor: UserContext,
    planId: string,
    expectedVersion: number
  ): Promise<ActivePlan>;

  requestRevision(
    actor: UserContext,
    input: RevisePlanInput
  ): Promise<JobRef>;
}
```

微信和网页调用相同的业务服务，避免两套修改规则。

## 12. 微信与提醒执行机制

微信通道必须先做真实验证，检查：

1. 多个内部账号如何绑定不同外部身份。
2. 用户消息能否可靠接收并识别归属。
3. 能否在计划时间主动发送提醒。
4. 主动发送的权限、窗口、额度和账号条件。
5. 回复延迟、重试和重启恢复。
6. 用户是否需要进入企业微信等额外入口。

不要将"支持聊天回复"等同于"支持任意时间主动提醒"。

建议统一消息契约：

```ts
type IncomingMessage = {
  channelInstanceId: string;
  externalEventId: string;
  externalUserId: string;
  conversationId: string;
  occurredAt: string;
  text: string;
};

type SendResult =
  | { status: "accepted"; externalMessageId?: string }
  | { status: "failed"; retryable: boolean; code: string }
  | { status: "unknown"; code: string };
```

回调型通道的处理顺序：

```text
验证签名、解密或完成通道规定的校验
→ 检查重放与事件重复
→ 持久化接收事件和处理任务
→ 按通道要求快速响应
→ worker 查询可信绑定，处理业务
→ 按实际通道能力发送结果
```

如果选定通道使用长连接或轮询，采用对应接收机制，不强行套用公网 webhook。

身份绑定必须使用短期、一次性凭证并证明双方身份，不能只让用户填写一个微信标识就绑定成功。

提醒执行顺序：

```text
计划生效事务
→ 保存新版本
→ 替代旧版本
→ 取消未发送的旧提醒
→ 创建新提醒
→ 提交事务

worker 领取到期提醒
→ 再检查计划版本与任务状态
→ 检查暂停、免打扰和频率限制
→ 写入发送任务
→ 通道发送
→ 记录发送结果
```

可靠性要求：

- worker 使用锁租约领取任务，崩溃后可以恢复。
- 明确每类错误是否重试，采用有限重试与退避。
- 已过时的提醒按策略跳过或合并。
- 通道接受请求只记为"已接受"，除非有送达证据，不记为"用户已收到或阅读"。
- 网络超时可能导致结果未知。优先使用通道幂等或查询能力；不能承诺跨外部系统绝对不重复发送。
- 无法确认结果时避免无限重发，并保留可排查状态。
- 发送已开始时的极小竞态要有记录，不宣称计划更新能撤回所有已在途消息。

## 13. 数据保护与管理权限

落实到代码的要求：

- API Key 仅在服务端保存，不返回完整密钥给浏览器。
- 密钥加密保存，主密钥与数据库备份分开管理。
- 不在 Git、普通日志或错误报告中写入密钥。
- 常规日志以用户内部 ID、任务 ID、耗时和状态为主，避免记录完整私人对话。
- 管理后台默认展示账号和运行数据，不提供随意浏览私人档案与聊天的功能。
- 明确托管服务器和数据库管理员仍可能接触数据，不能声称端到端加密。
- 删除记忆后，从后续模型上下文中排除。
- 账号删除处理个人数据、会话和未执行任务；备份中的删除时效需要在运维规则中说明。
- 服务商地址由受限的管理员配置，并防止访问云元数据或不允许的内部地址。
- 所有网页/API 权限都由后端检查，不能仅隐藏前端按钮。
- 登录、聊天和模型生成接口设合理限流与输入大小限制。

## 14. 测试与验收

测试重点应覆盖实际风险。

| 场景 | 验收标准 |
| --- | --- |
| 用户 A 请求用户 B 的目标、计划或聊天 | 拒绝访问，且不泄露内容 |
| 模型生成越权的目标 ID | 校验失败，不写入 |
| 固定安排与 AI 行动冲突 | 拒绝保存为生效计划，修复或返回说明 |
| 生成中用户修改档案 | 检测版本变化，不覆盖新状态 |
| 同时生成两个计划 | 最终只有一个有效生效版本 |
| 网页与微信同时修改 | 通过版本检查处理冲突 |
| 修改计划后旧提醒到期 | 旧提醒不再正常派发 |
| 同一回调重复投递 | 不重复创建业务变更 |
| worker 领取任务后崩溃 | 租约到期后可恢复 |
| 用户切换模型 | 档案与计划保留，后续调用使用新模型 |
| 模型输出无效 JSON | 有限修复，失败不破坏原计划 |
| 用户没有回复 | 状态保持未知 |
| 用户暂停提醒 | 后续发送检查能识别暂停 |
| 微信返回明确失败或结果未知 | 状态与重试策略正确 |
| 备份恢复到干净环境 | 能恢复用户、计划和必要配置 |

规划质量另外用生活案例评估：目标过多、临时加班、整天有课、疲劳、娱乐超时、不同作息等。

模型回复措辞可以变化，关键约束和状态行为必须稳定。真实微信验收与模拟通道测试分别记录。

## 15. 实施阶段与完成条件

| 阶段 | 实施内容 | 完成条件 |
| --- | --- | --- |
| P0 可行性验证 | 微信实测、候选仓库与许可证核验、两家模型调用 | 记录可用能力、限制和接入路线 |
| P1 项目基础 | 目录、认证、数据库、用户设置、档案和目标 | 两个账号互相隔离，可维护个人情况 |
| P2 规划核心 | 模型适配、上下文、结构化计划、校验、版本、进度 | 网页完成生成、接受、反馈、调整闭环 |
| P3 后台执行 | 数据库任务、worker、提醒更新、恢复和重试 | 模拟通道通过重启与并发测试 |
| P4 微信闭环 | 绑定、接收、发送、去重、业务服务接入 | 多用户真实微信收发与提醒验证通过 |
| P5 小范围试用 | 部署、备份、监控、额度、持续使用 | 记录并修复误记、过度安排、漏提醒和打扰 |

P0 的微信验证应尽早开始。若等待外部账号或配置，可以继续独立开发网页和规划业务，但真实微信功能保持"未验收"。

上线部署至少包含：

```text
HTTPS 入口
  └─ web

worker
  └─ PostgreSQL

web 与 worker 共享业务数据库及必要配置
数据库不直接暴露到公网
```

运维文档必须说明启动、数据库迁移、备份、恢复、密钥轮换和异常处理。健康检查还应能观察 worker 是否持续工作，仅网页在线不足以证明提醒正常。

## 16. 给接手 agent 的执行要求

接手后请按以下顺序开展工作：

1. 阅读本规划与工作区 `AGENTS.md`，确认当前阶段是设计还是已获准实施。
2. 创建或更新需求、架构决策和通道验证文档。
3. 对候选 GitHub 项目记录核验日期、版本、许可证与实测结论。
4. 优先验证微信通道；缺少账号或权限时明确指出，不用模拟结果代替真实结果。
5. 采用新建业务项目的默认路线，只有发现有证据支持的更优方案时才提出调整。
6. 实施时先打通"登录 → 个人情况 → AI 规划 → 反馈调整"，再接入可靠提醒与微信。
7. 完成关键测试后报告实际结果，不把编译通过等同于业务验收通过。
8. 持续维护已完成、未完成、待外部条件三类状态。

最终应交付：

- 可运行的源码与锁定依赖。
- 数据库迁移与示例配置。
- 模型和通道接入说明。
- 启动、部署与运维文档。
- 核心功能及多用户隔离测试。
- 真实模型、真实微信的验证记录。
- 清晰的未完成项与已知限制。

**本规划书本身不代表已验证仓库、完成代码或获得外部部署授权。用户当前要求是形成可交接的完整规划，后续实施依据明确的开发指令开展。**
