**核验对象**：AI 个人生活助手的微信通道候选方案（4 个开源项目）
**核验人**：P0 可行性核验
**检查日期**：2026-11-03
**核验结论适用范围**：仅覆盖 2026-11-03 当天抓取到的公开信息，不构成对运行时行为的保证。所有涉及"能不能真的推送到用户"的判断，最终都必须实测。

### 1.2 需要特别说明的两处仓库事实

1. **`zhayujie/chatgpt-on-wechat` 已改名。** 访问该 URL 会被 GitHub 重定向到 `zhayujie/CowAgent`（API 返回的 `full_name` 为 `zhayujie/CowAgent`）。README 末尾有《Project Renaming Notice》明确说明"本项目原名为 chatgpt-on-wechat，现正式更名为 CowAgent，旧 GitHub URL 自动重定向"。因此本记录中该条目按 **CowAgent** 记录，元数据取自改名后的仓库。
2. **Dify 的许可证不是标准 Apache-2.0。** GitHub API 返回 `license.spdx_id = NOASSERTION`、`name = Other`。必须抓 LICENSE 原文才能判断，不能按 Apache-2.0 处理。原文见 2.3。

### 1.3 没抓到 / 抓取失败的内容

- AstrBot 企业微信应用文档页（`docs.astrbot.app/platform/wecom.html`）：2 次尝试均报 `fetch failed` / 超时。
- AstrBot 统一 Webhook 模式文档页（`docs.astrbot.app/use/unified-webhook.html`）：超时。
- CowAgent Chat API 文档页（`docs.cowagent.ai/extensions/chat-api`）：2 次尝试均报 `fetch failed`。
- 上述内容一律在表格中标注"未获取到"或"文档未明确"，**未根据印象补全**。

### 1.4 方法局限

- 全部信息来自公开文档与 GitHub API，**未克隆代码、未部署、未实测任何一条消息推送**。凡"是否真能推送到任意注册用户"的结论，都是基于文档声明的推断，不是实测结果。
- 未获取任何仓库的 commit 总数，也未做代码级审计（如鉴权实现、数据库 schema、并发模型）。
- star/fork 是抓取时刻的快照，会持续变化。
- 微信平台的主动推送限制属于**平台规则**，不是这些开源项目能决定的。项目文档写了"支持发送"，不等于微信允许向任意用户随时发送。这是本次核验最重要的认知前提。

| **微信能力——能否主动推送给任意用户** | **不能作为可用能力。** 两层原因：<br>① **缺 API**：对外 HTTP API 只有 bot 生命周期与配置管理（创建/启停/重启/重出二维码/二维码分享/LLM profile/技能同步/SSE 事件流），**没有任何"发送消息给某个微信用户"的接口**，也没有会话消息接口 → 外部系统无法通过它主动推送。<br>② **底层同源限制**：它走的是腾讯官方个人微信接口，与 CowAgent 同一类通道；CowAgent 文档明确该通道有 24 小时主动推送窗口 → weclaws 上**大概率同样受限，待实测**（其 README 与 manuals 未提及该限制） |
| **多用户能力** | **明确支持，是它最强的部分。** 首个管理员自举 + 邀请码注册 + 多用户账号体系；每个用户独立的 bot、模型配置（每条含 provider/model/apiKey）、workspace、沙盒执行环境（`@fastagent/sandbox-runtime` 按用户分配进程池）；bot 路由均要求登录且"只能访问自己的 bot"；有 `BOT_LIMIT_REACHED` 配额。与我们的"多用户 + 邀请制"高度同构 |
| **接入方式** | HTTP API 存在且有文档（统一 `{ data, error }` 信封、结构化错误码、SSE 事件契约 `bot.status.updated` / `bot.qrcode.updated` / `bot.event.created` / `bot.error.updated`），鉴权为 Better Auth 登录态 + 管理员路由。**但契约范围只到"管理 bot"，不含"收发消息"**，因此**不能作为消息桥接服务被外部系统调用**，只能作为控制面 |
| **持久化（重启后恢复）** | 设计上明确：**SQLite 是控制面的事实来源**，网页只写"用户希望 bot 运行"的持久化意图（`desiredState`），supervisor 拥有运行时并持续 reconcile 收敛；有 `restartRequestedAt` / `qrReissueRequestedAt` / heartbeat / 数据库迁移。微信登录态、会话、待处理任务的具体恢复行为**文档未明确**（由底层 CLI 持有）→ 待实测 |
| **部署成本** | 中等偏高。Docker Compose 需 4 个服务：web、supervisor、sandbox-runtime、browserless。要求 Node.js 20+、pnpm、`BETTER_AUTH_SECRET`、`APP_BASE_URL`、`WEB_ADMIN_EMAILS`；数据库为 SQLite（无需外部 PG/Redis，是优点）。sandbox 镜像预装 Node20/bun/pnpm/python3/uv/ffmpeg/bubblewrap 等，镜像较重。另有**关键外部依赖风险**：真正的微信收发与工具执行在 `@fastagent/cli`（npm 包）里，**该包是否开源、许可证为何，本次未核实** |
| **结论** | **仅可参考设计**<br>理由：它的多用户控制面、`desiredState` + supervisor 收敛、邀请制账号体系非常值得借鉴，且技术栈与我们一致（TypeScript + Next.js）；但它没有任何消息收发 API，微信能力仅个人号扫码，无法充当桥接服务，且核心运行时依赖闭源性未知的 npm 包、项目活跃度偏低。 |

## 4. 对本项目的建议

### 4.1 最关键的结论：没有任何一个项目能直接满足"给任意注册用户主动推送"

这不是四个项目的实现问题，而是**微信平台规则**问题。按抓到的文档：

- 个人微信号（无论 AstrBot、CowAgent、weclaws 谁的实现）走的是腾讯官方接口，**主动推送受"用户最后一条消息后 24 小时"窗口约束**（CowAgent 文档明确写出）。超出窗口，定时提醒会失败，直到用户再发一条消息。
- 个人订阅号**不能主动推送**，只能先回占位消息，等用户再发一条才取回内容。
- **企业服务号（需认证 + 客服 API 权限）可以主动推送**——这是文档中唯一被明确写为"可主动推送"的微信路径。

**因此，"通过微信提醒"这一核心链路的产品设计，必须先按下面的顺序决策，再谈选哪个开源项目：**

1. 若必须"随时可提醒任意用户"→ 唯一可靠路径是**企业微信应用 / 微信客服 / 认证企业服务号**，且需要企业资质；个人号扫码方案只能作为"用户活跃期内的补充渠道"。
2. 若接受"24 小时内可提醒，超窗口则降级"→ 个人号方案可用，但产品上必须有降级策略（如超窗口改发短信/邮件/App 内通知，或引导用户回一条消息来重置窗口）。
3. 无论哪条路径，**"待处理任务"必须由我们自己的 worker + PostgreSQL 持久化并重试**，不能依赖通道项目自己的定时任务——否则窗口一过就静默丢失。

### 4.2 逐项目建议

| 项目 | 建议 | 理由 |
| --- | --- | --- |
| **CowAgent** | **作为首选桥接候选，进入实测** | ① MIT 许可，闭源商用无摩擦，是四个里唯一没有法律前置条件的；② 微信渠道覆盖最全（个人号/订阅号/服务号/微信客服/企微应用/企微机器人）；③ 唯一在文档里把"哪个渠道能/不能主动推"写清楚的项目，风险可预期；④ 活跃度健康（commit 距检查日 1 天，release 月度节奏，open issues 仅 51）。<br>待解决：多用户隔离需外层自建（推荐"每用户一实例 + 我们自己的用户库映射"），Chat API 契约待实测。 |
| **AstrBot** | **作为第二候选，与 CowAgent 二选一** | 优势是**框架层直接提供"按 UMO 主动发消息"的 HTTP API**，这对"我们自己的 worker 主动触发提醒"是最贴合的契约；通道也全。<br>主要顾虑：AGPL-3.0 的源码开放义务（若我们以 SaaS 形式对外提供，需评估是否愿意开源或做进程隔离的法务论证）；个人微信推送窗口文档未明确，必须实测。 |
| **weclaws** | **只借鉴设计，不作为通道** | 它的多用户控制面设计与我们的目标同构，值得直接抄的三点：① **SQLite/DB 作为唯一事实来源，网页只写意图（`desiredState`），由 supervisor 收敛运行时**——这正是我们"Next.js web + 独立 Node worker"该有的职责划分；② 邀请码注册 + 管理员自举 + `BOT_LIMIT_REACHED` 配额；③ 每用户独立模型配置（provider/model/apiKey 不落全局 env）。<br>但它**没有任何消息收发 API**，微信仅个人号扫码，且依赖闭源性未知的 `@fastagent/cli`、项目 1.5 个月无提交、star 仅 52。 |
| **Dify** | **排除** | ① 完全没有微信接入，无法承担提醒与双向对话；② 许可证明确禁止未经书面授权运营多租户，与本项目"多用户邀请制"直接冲突；③ 部署成本（2C4G 起步、十余个容器、PG+Redis+向量库）与一个 P0 验证阶段完全不匹配。 |

### 4.3 对架构的直接影响

1. **不要把微信通道写进主链路的核心抽象里。** 应定义我们自己的 `ChannelAdapter` 接口（`sendProactive(userId, content)` / `onInbound(message)` / `getDeliveryWindow(userId)`），把 CowAgent/AstrBot 放在适配器后面。理由：本次核验显示四个项目的对外契约差异极大（AstrBot 有 HTTP 主动消息 API、CowAgent 有 Chat API 但契约未明、weclaws 根本没有），且微信平台规则可能随时变化，通道必须可替换。
2. **`getDeliveryWindow` 必须是一等公民。** 因为 24 小时窗口是硬约束，"能不能推"要在数据模型里表达（记录用户最后一条入站消息时间），而不是等推送失败再补救。
3. **待处理任务归我们自己的 worker 管。** 用 PostgreSQL 存任务与重试状态，通道项目只负责"送出去"这一件事。这样既满足"重启后待处理任务可恢复"，也让换通道不影响业务数据。
4. **P0 阶段不要引入 Dify 这类重量级依赖。**

### 4.4 建议的下一步（P0 收尾动作）

1. 用**同一个微信号**分别实测 CowAgent 与 AstrBot 的个人微信通道：登录 → 收消息 → **静置 24 小时后由外部 HTTP 接口主动推送**，记录是否失败及错误码。这是本次核验唯一无法从文档得出结论的关键项。
2. 实测 CowAgent 的 Chat API（端点/鉴权/回调），补齐本次未获取到的契约。
3. 确认 `@fastagent/cli` 的开源状态与许可证（若考虑 weclaws，这是前置条件）。
4. 就 AGPL-3.0 的"网络服务"边界咨询法务，再决定 AstrBot 是否可用。
5. 若企业资质可得，优先评估**企业微信应用 / 认证企业服务号**路径——这是文档层面唯一能"随时主动推送"的通道。
