## 1. 项目缘起

### 1.1 一句话目标

做一个 **AI 个人助手**：

1. 有一个**前端页面**，可以调用大模型、录入**个人信息**（具体字段待补充）；
2. 助手能"记住我"，并能在**微信上提醒我今天要做的事情**；
3. 同时支持**在微信里直接和助手对话**（不是在网页里聊）。

### 1.2 前置调研：WeClaws

在明确需求前，先调研了 GitHub 上的 [yokingma/weclaws](https://github.com/yokingma/weclaws)。结论是**不采用**，但有几条设计思路值得抄。

| 项 | 值 |
| --- | --- |
| 定位 | 自托管、多用户的微信 AI 智能体**控制台**（control plane） |
| 语言 / 许可 | TypeScript / MIT |
| Stars / Forks | 52 / 7 |
| 创建 / 最近推送 | 2026-05-07 / 2026-09-17 |
| 技术栈 | Next.js + Better Auth + SQLite(Drizzle) + Docker Compose |
| 组成 | `apps/web`、`apps/supervisor`、`packages/db`、`packages/shared`、`infra/` |
| 执行引擎 | 依赖外部 `@fastagent/cli`（微信通道、工具、MCP、技能、记忆、定时任务、沙盒） |

它的核心原则（值得借鉴）：

- **SQLite 是控制面唯一事实来源**，网页只写"运行意图"，不把内存当事实；
- **网页不管进程**，supervisor 独占运行时并持续收敛状态；
- 执行引擎通过**外部契约（JSONL 事件流）**接入，不依赖其内部结构。

### 1.3 调研结论

- WeClaws 解决的是"**部署一次、多人长期托管**"的问题，不是"单用户定时提醒"。
- 对本项目属于**过重方案**：引入 supervisor、多用户、沙盒、browserless sidecar 都无必要。
- 但三条思路直接沿用：
  1. 控制面与执行面分离（前端只配置，执行另有其物）；
  2. 状态落库、不以内存为真相（服务器重启后仍能恢复）；
  3. **推送通道做成可替换的接口**（重要，见第 5 章）。

### 1.4 同名项目澄清

另有一个只差一个字母的项目 **WeClaw**（[shp-ai/weclaw](https://github.com/shp-ai/weclaw)），是微信 ↔ 编程 agent 的**桥接器**（Go 单二进制，`weclaw login && weclaw start`），用于在微信里指挥 Claude Code / Codex / Cursor 等本地 agent。与本项目需求无直接关系，但它的"**微信 ↔ 任意后端**"思路可参考。

## 3. 需求拆解

### 3.1 模块划分

```
┌─────────────┐   ┌──────────────┐   ┌──────────┐   ┌────────────┐
│ ① 前端页面   │   │ ② 个人信息库  │   │ ③ 大脑    │   │ ④ 微信触达  │
│ 录入 / 对话  │──▶│ 结构化档案    │──▶│ 大模型    │──▶│ 定时提醒    │
│ 看待办 / 历史│   │ + 记忆检索    │   │ 生成内容  │   │ 双向对话    │
└─────────────┘   └──────────────┘   └──────────┘   └────────────┘
                                            ▲
                                     ┌──────┴──────┐
                                     │ ⑤ 定时器     │
                                     │ cron 每日触发 │
                                     └─────────────┘
```

### 3.2 模块职责

| 模块 | 职责 | 关键点 |
| --- | --- | --- |
| ① 前端页面 | 录入个人信息、管理待办、查看提醒历史、调试对话 | 不做成聊天 App，定位是"配置台" |
| ② 个人信息库 | 存结构化档案 + 自由笔记 | 两层分离，见第 6 章 |
| ③ 大脑 | 调模型：生成早报、回答问题、从聊天提取待办 | 日期等事实由代码算好注入，不让模型算 |
| ④ 微信触达 | 收消息（回调）+ 发消息（主动推送） | **全项目风险最高的一环**，见第 5 章 |
| ⑤ 定时器 | 每天固定时间触发早报；到点触发事件提醒 | 需处理时区、漏推补偿 |

### 3.3 「今日提醒」的最小链路

```
cron 每天 07:30
  → 查今天到期的待办 + 结构化档案
  → 拼 prompt（日期、星期、待办、偏好）
  → 调大模型生成一段人话
  → 调用推送通道发到微信
  → 结果与耗时写库（便于排查）
```

这条链路**不需要 agent，不需要 tool calling**，一天一次调用，成本几乎为零，失败可重试。这是 MVP 的主线。

## 5. 微信通道选型（未定）

### 5.1 为什么这一章最关键

个人微信**没有官方的"给任意人发消息"接口**。所有方案都是绕路，区别只在于**绕哪条路、代价是什么**。而"要双向聊天"这一条，直接淘汰了一半方案。

### 5.2 方案对比

| 方案 | 免费 | 双向 | 使用体验 | 主要代价 |
| --- | --- | --- | --- | --- |
| **企业微信自建应用** + 微信插件 | 是 | ✅ | 中：需跳转企业微信查看/回复 | 需注册企业主体；未认证企业有 200 人上限；回调需公网 HTTPS |
| **扫码登录个人微信**（协议/Wechaty 一类） | 是 | ✅ | **最好：原生微信聊天** | **违反微信规范，有封号风险**；协议易失效需持续维护 |
| 公众号（认证服务号） | 否（约 300 元/年） | ✅ | 中 | 个人主体无法认证服务号 |
| 公众号测试号 | 是 | 半 | 差 | 仅适合验证，接口受限、不稳定，不适合长期 |
| Server酱 / PushPlus | 有免费额度 | ❌ | 好 | **只能推不能收，已不满足需求** |

### 5.3 初步倾向（待你确认）

- 若微信号是**主号、不能承受封号** → 走**企业微信自建应用**，官方通道、稳定、免费。
- 若愿意用**小号、追求原生体验** → 走扫码登录方案，但需接受"随时可能失效/被封"。
- 无论选哪个，**推送层都抽象成统一接口**（`sendMessage(userId, content)` / 回调统一归一化），保证未来可换。

### 5.4 "要双向"带来的新增硬性条件

| # | 条件 | 说明 |
| --- | --- | --- |
| A1 | **公网 HTTPS 入口** | 微信回调只接受 80/443 且需可验证，国内服务器还必须**域名备案**（约 1–3 周） |
| A2 | **异步应答** | 微信回调有秒级超时，大模型生成远超此限：必须先回 ack，再主动推送结果 |
| A3 | **消息幂等** | 回调会重试，必须用 MsgId 去重，否则一条消息被处理两次 |

## 6. 个人信息的设计（字段待补充，结构先定）

建议**从一开始就分两层**，不要只做一个大文本框：

| 层 | 存什么 | 用途 | 例子 |
| --- | --- | --- | --- |
| **结构化档案** | 稳定、每次都需要的字段 | 每次拼 prompt 都带上，稳定可控 | 姓名、职业、作息、长期目标、语气偏好、免打扰时段 |
| **自由笔记** | 随手记、聊天中沉淀的事实 | 需要时做语义检索（RAG） | "最近在减脂"、"下月要搬家" |

理由：只做"自由文本 + 向量检索"会导致模型**时好时坏地记住你**；而固定字段（作息、语气）必须每次在场。两类信息混在一起处理，两边都做不好。

**结论：你说字段后面补充，但表结构可以现在就定，后续只加字段、不改架构。**

## 7. 待讨论：我看到的盲区清单

> 这是你要求"补充我没想到的点"的部分。每条标注优先级：
> **P0** = 开工前必须定，否则会返工；**P1** = 首个可用版本内要处理；**P2** = 可以后补。

### A. 微信通道与合规（7 条）

| # | 优先级 | 问题 |
| --- | --- | --- |
| A1 | P0 | 双向聊天需要**公网 HTTPS**：域名 + 备案 + 证书。国内服务器 80/443 未备案会被拦。**这是最容易漏掉的时间成本（1–3 周）** |
| A2 | P0 | 通道选型未定：企业微信（官方、稳、体验需跳转）vs 扫码协议（体验原生、有封号风险）。**取决于你用主号还是小号** |
| A3 | P0 | 微信回调超时约 5 秒，模型生成远超此限 → 必须异步：先 ack、后主动推送。**这决定要不要任务表/队列** |
| A4 | P1 | 回调会重试 → 必须按 MsgId 幂等，否则待办被记两条 |
| A5 | P1 | 微信侧有内容安全审核，模型输出敏感内容可能被拦，极端情况影响账号 → 输出需兜底过滤 |
| A6 | P1 | 用户可能发**语音/图片** → 需要 ASR 或视觉模型，是隐藏工作量。MVP 建议先只支持文本并明确提示 |
| A7 | P2 | 群聊场景：只在私聊响应，还是群里 @ 才响应？用扫码协议会涉及群消息，需明确边界 |

### B. 数据与隐私（5 条）

| # | 优先级 | 问题 |
| --- | --- | --- |
| B1 | P0 | 个人信息（健康/财务/人际关系）会被送到第三方大模型 API → 需明确：**哪些字段绝不外发**、是否脱敏、用境内还是境外模型（境外涉及数据出境） |
| B2 | P0 | 网页部署在公网**必须至少登录鉴权**，否则等于把个人档案公开在互联网上 |
| B3 | P1 | API Key、微信凭据、数据库的存放与轮换；**严禁进 git** |
| B4 | P1 | 备份与恢复：SQLite 是单文件，需定期快照到对象存储，否则服务器故障 = 记忆全丢 |
| B5 | P2 | 聊天记录留存期限与删除入口（自己也可能想删） |

### C. 可靠性与成本（7 条）

| # | 优先级 | 问题 |
| --- | --- | --- |
| C1 | P0 | 时区固定 `Asia/Shanghai`；**所有日期由代码算好后注入 prompt**，绝不让模型算"明天"——这是高频错误源 |
| C2 | P0 | 漏推补偿：服务器宕机/重启后，早报是补发、跳过还是合并？补发要避免半夜轰炸 |
| C3 | P1 | 推送失败必须能自知：加心跳 + 兜底通道（邮件/短信），否则"没收到"和"没推送"无法区分 |
| C4 | P1 | 上下文成本控制：记忆不能无限塞，需分层（档案常驻 + 笔记按需检索 + 历史压缩），否则账单随天数线性上涨 |
| C5 | P1 | 模型幻觉：编造不存在的待办、把已完成说成未完成 → prompt 强制"只允许使用给定数据"，代码层再做事实校验 |
| C6 | P1 | 微信对话是碎片化、跨天的，需要会话切分策略（按天？按主题？） |
| C7 | P2 | 模型 API 限流/超时/降级（主模型挂了换备用） |

### D. 产品与体验（9 条）

| # | 优先级 | 问题 |
| --- | --- | --- |
| D1 | P0 | 提醒时间可配置 + **免打扰开关**（"今天别烦我"、出差模式） |
| D2 | P0 | 待办其实分两类：**定时事件**（15:00 开会，需提前 N 分钟提醒）与**全天任务**（写周报，只需早报）→ 两套触发机制，别混成一个 cron |
| D3 | P0 | 聊天自动提取待办会**误记**，需要回执确认（"已记录：xxx，回复 撤销 取消"），否则清单很快变脏 |
| D4 | P1 | **重复任务**（每周一开会、每月还信用卡）需要 recurrence 规则——待办系统里最容易被低估、也最容易做崩的部分 |
| D5 | P1 | 双端一致性：网页改待办 ↔ 微信记待办，必须**同一数据源**，不能各存一份 |
| D6 | P1 | 助手在微信里的能力边界：只"回答 + 记待办"，还是也能"改档案/删待办/查天气"？决定要不要 tool calling，工作量差 2–3 倍 |
| D7 | P2 | **日终复盘**（晚上问"今天这几件做完了吗"）价值很高，但会变成每天两条消息，需你确认接受度 |
| D8 | P2 | 语气/人设可配置（"简洁" vs "唠叨"），本身应作为档案字段 |
| D9 | P2 | 首次使用引导（`/help`），否则一周后自己都忘了能发什么命令 |

### E. 工程与运维（6 条）

| # | 优先级 | 问题 |
| --- | --- | --- |
| E1 | P0 | **MVP 范围要划死**：只做"文本聊天 + 手动录入 + 早报"，还是一开始就上语音/图片/重复任务？范围膨胀是这类项目最大的死因 |
| E2 | P1 | 本地调试微信回调需内网穿透（cpolar/frp/ngrok），且微信只接受 80/443 |
| E3 | P1 | 部署形态建议 Docker Compose + 进程守护（systemd），便于迁移与回滚 |
| E4 | P1 | 数据库 migration 工具（Drizzle/Prisma），表结构后面一定会改 |
| E5 | P2 | 日志与监控：至少 `/health` + 结构化日志，能定位是"收消息/调模型/推送"哪一步挂了 |
| E6 | P2 | **预留 `user_id` 字段**（哪怕现在单人），未来给家人用成本极低，事后加成本很高 |

| --- | --- |

## 附录 A：术语表

| 术语 | 含义 |
| --- | --- |
| 控制面 / 执行面 | 前者管"配置与状态"，后者管"真正干活"。分离是为了重启不丢状态 |
| 回调（callback） | 微信把用户消息 POST 到你的服务器地址 |
| 幂等（idempotent） | 同一条消息处理多次，结果与处理一次相同 |
| recurrence | 重复规则，如"每周一" |
| RAG | 检索增强生成：先检索相关笔记，再交给模型 |
