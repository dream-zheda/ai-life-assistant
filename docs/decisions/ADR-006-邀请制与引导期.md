# ADR-006：邀请制与引导期

- 状态：已采纳
- 日期：2026-11-03
- 相关：`apps/web/src/server/invites.ts`、`apps/web/src/server/auth.ts`、`scripts/verify-invites.ts`

## 背景

规划书 §3 把「邀请注册」列为第一版要求，但此前的实现是**任何能打开 `/sign-up` 的人都能注册**——
与"邀请制"定位不符，也是 P1 的最后一个缺口。

## 决策

### 1. 拦截点放在 `databaseHooks.user.create.before`

```ts
databaseHooks: {
  user: { create: { before: async (user, context) => { ... } } }
}
```

而不是放在页面或某个 API 路由里。理由：**所有注册路径都会经过这个钩子**——
不管前端怎么调、有没有走我们自己的表单、将来接入第三方登录也一样。
放在页面里只能挡住"通过那个页面"的人。

### 2. 数据库只存 sha256 摘要

明文令牌只在创建时打印一次，之后无法从库里还原。
即使数据库被读走，也拿不到可用的邀请码。

创建方式（管理员）：

```powershell
& $pnpm invite:create 管理员邮箱@example.com 72
# 输出：邀请码 / 有效期 / 邀请链接
```

### 3. 一次性靠条件更新，不靠"先查后写"

```ts
await prisma.invite.updateMany({
  where: { tokenHash, usedAt: null, expiresAt: { gt: now } },
  data: { usedAt: now },
});
```

并发下只有一个请求能把这个字段从 `NULL` 改成时间戳。先查后写会有竞态。

### 4. 引导期例外：库里没有用户时放行

否则会死锁：注册需要邀请码 → 创建邀请码需要管理员 → 管理员需要注册。

规则：

- `users` 表为空 → 允许无邀请码注册，且第一个用户自动成为 `ADMIN`
- 之后一律需要邀请码

代价：**部署完到第一个账号注册之间的窗口是敞开的**。所以首次部署必须立刻注册管理员，
runbook 的首次验收清单里已经写明。

### 5. 限流保留，但给测试留开关

Better Auth 默认开启登录/注册限流（60 秒 10 次）。端到端验证要连发多个注册请求，
会被 429 拦下——**第一版验证脚本就是因为这个误判成"邀请码只能一次"失败**。

```ts
rateLimit: { enabled: process.env.AUTH_RATE_LIMIT !== "off", window: 60, max: 10 }
```

生产必须保持开启。关掉只用于自动化验证。

## 验证（真实 HTTP，不是"能编译"）

`scripts/verify-invites.ts` 会清空用户表后完整走一遍：

| 场景 | 结果 |
| --- | --- |
| 引导期首个用户注册 | 200 |
| 首个用户自动成为 ADMIN | `role=ADMIN` |
| 引导期结束后无邀请码注册 | 400「注册需要邀请码」 |
| 持有效邀请码注册 | 200 |
| 同一个码用第二次 | 400「邀请码已被使用」 |
| 过期邀请码 | 400「邀请码已过期」 |
| 邀请码记录使用者 | `usedById` 指向新用户 |

