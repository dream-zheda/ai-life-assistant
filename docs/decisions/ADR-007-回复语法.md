# ADR-007：微信侧的回复语法——为什么早报不能写「回复 1/2/3」

- 状态：已采纳
- 日期：2026-11-03
- 相关：`packages/channels/src/reply.ts`、`packages/channels/src/render.ts`、`apps/worker/src/inbound.ts`

## 背景

提醒消息里写了「回复 1 完成」。如果没人解析这句话，就是**给用户一个无效承诺**——
他照做了，系统毫无反应，比不写更伤害信任。

实现入站解析时，撞上一个必须先解决的歧义：

**早报里有多条安排，「1」到底是什么意思？**

- 「我完成了」（针对刚才提醒的那一项）
- 「第 1 项完成了」

两种解释都合理，而用户不可能知道我们心里想的是哪种。

## 决策

### 1. 单项提醒用裸数字，早报用带序号命令

| 消息 | 回复语法 | 为什么 |
| --- | --- | --- |
| 单项提醒（10 分钟后开始「背单词」） | `1` / `2` / `3` | 上下文只有一项，无歧义 |
| 每日早报（列出 5 项） | `完成 2`、`跳过 3` | 必须显式指定第几项 |

早报结尾因此改成：

```
回复「完成 2」标记第 2 项完成，「跳过 3」跳过第 3 项。回复「帮助」看全部指令。
```

**这是一条违反直觉的规则**：直觉上"统一用 1/2/3"更简单。但统一之后，
用户在早报下回「1」，我们无法判断他想标记哪一项——无论怎么实现都会有人被误解。

### 2. 裸数字靠「最近的提醒」定位

`1/2/3` 的目标条目 = 该用户在**最近 2 小时内**收到的 `START` 提醒对应的计划条目。

没有近期提醒时，**不猜**，直接回：

```
没找到要记录的那一项。回复「帮助」看看能做什么。
```

静默失败比多问一句更糟。

### 3. 带序号命令按当天计划顺序定位

`完成 2` = 当天最新计划版本里 `startsAt` 升序的第 2 项。

### 4. 已完成不可回退

重复回复「完成」不会叠加记录，也不会改写状态：

```
「背单词」已经记过完成了。
```

与 `packages/domain` 里的 `applyReport` 保持一致：`done` 是终态。

### 5. 自由文本不是指令

「今天下午要加班」这类文本返回 `unknown`，由后续对话能力处理，
不硬塞进进度记录。

## 后果

- 提醒文案与解析器必须**成对修改**。只改一边就会出现"提示还在、解析没了"或反之。
  这条已写进 AGENTS 的硬规则。
- `parseReply` 是纯函数，14 个单元测试覆盖全角数字、句末标点、序号越界等情况。
- `handleInboundMessage` 有 9 个集成测试（真数据库），包括**跨用户隔离**：
  B 回复「完成 1」不会影响 A 的条目。

## 未做的部分

| 事项 | 影响 |
| --- | --- |
| 真实入站通道 | 目前只有函数 + 控制台通道，没有 webhook / 长连接接收真实微信消息 |
| 「今天累了」自动重排 | 帮助文案里写了"该功能还在做"，**不要让它长期停在承诺状态** |
