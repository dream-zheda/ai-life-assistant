# ADR-002：微信通道选型与「推送窗口」的一等公民设计

> **2026-11-03 补充（待复核）**：本文中「24 小时」这个数字来自 CowAgent 的文档，
> 我们**没有实测来源**；业界对公众号客服消息窗口普遍引用的是 **48 小时**。
> 用它做产品决策前必须先复核并修正本文。
>
> 另外，项目所有者已决定改走「个人号协议登录」路线：那条路没有窗口限制，
> 但违反微信平台规则，代价见 [ADR-009](./ADR-009-个人号协议登录.md)。

- 状态：已采纳（通道最终选型仍待实测与资质确认）
- 日期：2026-11-03
- 依据：`docs/P0-仓库核验记录.md`、`docs/评审意见-v1.0.md` §1

## 背景：一个会改变产品前提的事实

P0 核验从公开文档中得到一条硬约束：

> **个人微信号（走腾讯官方接口）只能在用户最后一条消息之后 24 小时内主动推送。**
> 超出窗口，定时任务推送会失败，直到用户再次发消息。

来源：CowAgent 个人微信通道文档原文（AstrBot 使用同一底层接口但文档未提，按更严的一侧设计）。

同时：

- 个人订阅号**完全不能**主动推送（只能先回占位消息，等用户再发一条）。
- **认证企业服务号（需客服 API 权限）**是文档中唯一被明确写为「可主动推送」的微信路径。
- 企业微信自建应用可主动推送，但收件人必须是企业通讯录成员（未认证默认 200 人上限，已核验官方 FAQ）。

**对本项目的含义：**

产品的核心承诺是「每天早上提醒你今天的安排」。在个人微信通道上，只要用户超过 24 小时没跟助手说话，这条提醒**发不出去**。这不是 bug，是平台规则。

## 决策

### 1. 通道策略进入领域模型，而不是留到实现层

新增 `@life/channels`，把「这个通道允许多久内主动推送」变成数据：

```ts
type ChannelPolicy = {
  id: ChannelId;
  proactiveWindowMs: number | null;  // null = 平台不限制
  requiresRecipientOptIn: boolean;
  needsFallback: boolean;
  // ...
};
```

已入库的五种通道：个人微信（24h）、个人订阅号（0）、认证企业服务号（不限）、企业微信应用（不限）、微信客服（待实测）。

### 2. `decideProactiveDelivery` 是三态判断，不是布尔值

```ts
type DeliveryDecision =
  | { action: "send"; expiresAt: Date | null }
  | { action: "fallback"; reason: "never_contacted" | "window_expired"; hint: string };
```

**窗口关闭时不允许"尝试发送再失败"**。必须在派发前就算出结果，走降级分支。这样失败是可预期的，而不是每天早上的随机事故。

### 3. 数据模型必须记录 `lastInboundAt`

每个通道绑定都要存「该用户在本通道上最后一次给我们发消息的时间」。这是计算窗口的唯一输入，**不存储就无法判断能不能推**。

### 4. 通道能力放在 `ChannelAdapter` 后面，不在主链路里

```ts
interface ChannelAdapter {
  readonly policy: ChannelPolicy;
  send(message: OutboundMessage): Promise<SendOutcome>;
  verifySignature(headers, rawBody): boolean;
  parseInbound(headers, rawBody): InboundMessage | null;
}
```

`SendOutcome` 区分 `accepted` / `failed` / `unknown`，**没有 "delivered"**——通道接受 ≠ 用户收到。

### 5. 桥接候选排序

| 项目 | 结论 | 关键理由 |
| --- | --- | --- |
| **CowAgent**（原 chatgpt-on-wechat） | **首选桥接候选** | MIT 无法律摩擦；渠道覆盖最全；唯一把"哪个渠道能主动推"写清楚的项目 |
| AstrBot | 第二候选 | 框架层直接提供 `POST /api/v1/im/message` 主动消息接口，契约最贴合我们的 worker；但 **AGPL-3.0** 有源码开放义务，需法务评估 |
| weclaws | **只借鉴设计，不作通道** | 无任何消息收发 API。可借鉴：DB 存意图 + supervisor 收敛、邀请码注册、每用户独立模型配置 |
| Dify | **排除** | 无微信通道；许可证明确禁止未经书面授权运营多租户，与本项目直接冲突 |

## 后果

**必须接受的代价：**

- 若第一版只能用个人微信，**早报必须带降级策略**（邮件 / 站内 / 引导用户回一条消息重置窗口），并且要如实告知用户"这条提醒可能发不出去"。
- 若要做到"随时可靠提醒"，必须先解决**企业主体资质**（营业执照 + 微信认证，约 300 元/年）。这是流程性工作，周期以周计，**比写代码更需要提前启动**。

**获得的好处：**

- 换通道不影响业务数据与业务规则（`ChannelAdapter` 在后面）。
- 窗口问题在数据层就暴露，不会等到 P5 试用期才发现漏推。
- 5 个通道策略已有 9 个单元测试覆盖边界（24h 整点、订阅号窗口为 0、服务号不受限）。

## 未决事项

| # | 事项 | 为什么未决 |

## 附录：为什么不用「24 小时内提醒」伪装成「每天提醒」

一种取巧做法是：每天只在用户当天发过消息时才推早报。但这会把产品变成"你得先跟我说话，我才提醒你"，与「助手主动照顾你」的定位相反。**宁可在产品上明确降级并告知，也不要制造"有时能收到有时收不到"的不确定体验。**
