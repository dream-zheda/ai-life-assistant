# ADR-008：计划生效（DRAFT → ACTIVE）是必经步骤

- 状态：已采纳
- 日期：2026-11-03
- 相关：`apps/web/src/server/plan-activation.ts`、`apps/worker/src/reminders.ts`

## 背景：一个被拼错的链路

各模块单独看都是对的：

| 模块 | 行为 |
| --- | --- |
| `packages/planning` | 生成计划，校验通过 |
| `apps/web` 的 `generateTodayPlan` | 把计划写成 `state = 'DRAFT'` |
| `/today` 页面 | 展示最新版本的计划与条目 |
| `apps/worker` 的 `enqueueStartReminders` | 只为 `planVersion.state = 'ACTIVE'` 的条目生成提醒 |

**串起来的结果是：用户点「生成计划」→ 生成成功 → 永远不会收到任何提醒。**

计划永远停在 DRAFT，而 worker 只认 ACTIVE。这是我在做「提醒」那轮之后、
回头核对链路时才发现的——因为每一层都通过了各自的测试。

## 决策

### 1. 采纳必须由用户触发，不自动生效

规划书 §6 要求「初次计划需要确认」。生成即生效会让用户在没看过的情况下被安排一整天。

`activatePlanVersion` 是显式动作，对应 `/today` 上的「采纳这份计划」按钮。

### 2. 事务内先撤旧、再启新

```ts
await tx.planVersion.updateMany({ where: { ...state: "ACTIVE" }, data: { state: "SUPERSEDED" } });
await tx.planVersion.update({ where: { id }, data: { state: "ACTIVE" } });
```

顺序不能反：数据库上有「同一用户同一天只能有一个 ACTIVE」的**部分唯一索引**
（手写在 `migrations/*_constraints`）。先启新会在语句结束时立刻撞索引。

### 3. 采纳前丢弃已经结束的条目

计划是异步生成的，用户可能隔一阵才点采纳。完全过去的条目直接删掉，
跨在"现在"的保留（用户可能正在做）。一条都不剩时**拒绝采纳**并提示重新生成。

这和第 3 轮做的 `prepareActivation` 是同一类保护，只是这里作用在数据库侧。

### 4. 只接受 DRAFT

`SUPERSEDED` / `DISCARDED` 的版本不允许再被采纳——否则会出现"用旧版本覆盖新版本"。

## 后果

- 主链路终于闭环：**生成 → 采纳 → worker 生成提醒 → 派发 → 用户回复进度**
- 未采纳的计划不会产生任何推送，符合"确认模式"的语义
- 采纳后 worker 在下一个 tick（默认 15 秒）内生成提醒，无需额外触发
- 旧的 ACTIVE 版本被替代后，它的提醒会被 dispatcher 判为 `CANCELLED`（已有逻辑）

## 验证

`apps/web/tests/activation.int.test.ts`，6 个用例：

- 草稿变生效，已结束条目被丢弃（`droppedCount = 1`，`itemCount = 1`）
- 采纳新版本时旧版本变 `SUPERSEDED`，同一天只有一个 ACTIVE
- 重复采纳 → `already_active`
- 采纳别人的计划 → `not_found`，且目标计划仍是 DRAFT
- 条目全部过期 → `empty`，拒绝采纳
- 已替代的版本 → `superseded`

真实 HTTP：`/today` 对 DRAFT 计划显示「这份计划还没有生效 / 采纳这份计划」表单。

## 未做

| 事项 | 影响 |
| --- | --- |
| 自动模式（授权后自动采纳） | 规划书 §6 提到"后续允许配置自动规划"，未实现 |
| 采纳前预览差异 | 用户看不到"新旧计划差在哪" |
| 撤销采纳 | 只能重新生成一版并采纳 |
