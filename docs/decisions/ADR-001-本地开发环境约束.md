# ADR-001：本地开发环境与工具链约束

- 状态：已采纳
- 日期：2026-11-03

## 背景

开发机（Windows，工作区沙箱模式）的实测情况：

| 工具 | 状态 |
| --- | --- |
| Node.js | v24.19.0 ✅ |
| npm | 11.17.0 ✅（`npm.ps1` 被执行策略拦截，需走 `npm.cmd`） |
| git | 2.54.0 ✅ |
| pnpm | ❌ 未安装 |
| Docker | ❌ 未安装 |
| PostgreSQL | ❌ 未安装 |
| WSL | ❌ 未安装 |
| 磁盘可用 | 329 GB ✅ |

沙箱另外施加了三条限制（实测触发）：

1. **只允许写工作区目录。** npm 默认缓存目录（`%LOCALAPPDATA%\npm-cache`）不可写，报 `The operation was rejected by your operating system`。
2. **不允许 pnpm 重命名 `node_modules` 下的符号链接**，报 `EPERM: operation not permitted, rename ... -> .ignored/...`。
3. **不允许程序通过管道启动子进程**，报 `spawn EPERM`。影响所有走 `child_process.spawn(..., {stdio:'pipe'})` 的工具（esbuild、postinstall 脚本）。

## 决策

| 决策 | 取值 | 理由 |
| --- | --- | --- |
| 包管理器 | pnpm 9.15.4，装在 `<workspace>/.tools/pnpm/pnpm.cmd` | 装在 workspace 内，避免写系统目录；`corepack prepare` 在沙箱下失败 |
| npm 缓存 | `<workspace>/.npm-cache` | 规避限制 1 |
| pnpm store | `.pnpm-store`（项目内，见 `.npmrc`） | 同上 |
| node_modules 布局 | `node-linker=hoisted` | 规避限制 2；同时修复 vitest 传递依赖解析 |
| 安装脚本 | 一律 `--ignore-scripts` | 规避限制 3；esbuild 的二进制来自 `@esbuild/win32-x64` 可选依赖，跳过 postinstall 不影响 |
| 测试运行 | 需提升沙箱权限 | vitest 经 esbuild 启动服务进程，触及限制 3 |
| 数据库 | 本机**不跑** PostgreSQL | 无 Docker、无 Postgres、无 WSL |

## 后果

**可以做的：**

- `pnpm typecheck`：在沙箱内即可通过。
- `pnpm test`：需提权，43 个测试用例全部通过。
- Prisma schema 的 `prisma validate` / `prisma generate`：不需要数据库连接。

**不能做的：**

- `prisma migrate dev` / 任何需要真实数据库的集成测试。
- `docker compose up` 本地起 PostgreSQL。

**影响范围：**

本机限制**只影响本地开发**，不影响云服务器上的生产部署（那边有 Docker + PostgreSQL）。因此**不为了迁就本机而把数据库降级成 SQLite**——那会牺牲 `FOR UPDATE SKIP LOCKED` 任务队列、部分唯一索引、`timestamptz` 等规划书 §9 明确要求的约束。

## 备选方案（未采纳，备查）

| 方案 | 未采纳原因 |
| --- | --- |
| SQLite（Prisma）+ 后期迁移 | 需要放弃 enums/数组/部分唯一索引，迁移到 PG 时 schema 与迁移记录都要重写 |
| `embedded-postgres` npm 包 | 需下载平台二进制，尚未验证在沙箱下能否启动；留作后续尝试 |
| `pglite`（WASM Postgres） | Prisma 无官方 driver adapter，需换 ORM |
| 安装 WSL2 | 需要管理员权限与重启 |

## 附录：本地 PostgreSQL 已可用（2026-11-03 更新）

上面的「数据库」结论**已被推翻并解决**。`embedded-postgres` 在装好之后可以跑起来，
代价是要绕开三个 Windows 特有的坑。实现见 `scripts/dev-db.mjs`。

### 坑 1：中文路径被写进初始化 SQL

项目路径是 `C:\Users\<用户名>\Desktop\...`。`initdb` 在 post-bootstrap 阶段会把**工作目录**
写进初始化脚本，而脚本按 UTF-8 交给模板库；「马」的 GBK 编码是 `0xC2 0xED`，
恰好不是合法 UTF-8 序列，于是：

```
FATAL: invalid byte sequence for encoding "UTF8": 0xc2 0xed
```

`--locale=C` 只能解决另一条报错（找不到 `Chinese (Simplified)_China.936` 的全文检索配置），
**解决不了路径问题**。

解法的关键不是换数据目录，而是**换进程工作目录**：

```powershell
subst Y: "<项目根目录>"   # 只创建一次
```

然后脚本里 `process.chdir("Y:\\")`，数据目录用 `Y:\.pgdata`。路径全程 ASCII。

### 坑 2：数据目录不能放在工作区外

即使 `danger-full-access`，`initdb` 子进程写 `C:\Users\Public\...` 仍被拒。
所以数据目录必须落在工作区内 —— 这也是用 `subst` 而不是换盘符的原因：
数据实际仍在 `AI个人助手/.pgdata`，只是对外表现为 `Y:\`。

### 坑 3：system locale 是 CP936

`initdbFlags: ["--encoding=UTF8", "--locale=C", "--lc-collate=C", "--lc-ctype=C"]`。

### 现在的能力

| 命令 | 作用 |
| --- | --- |
| `pnpm db:up` | 起库并保持运行（开发服务器用） |
| `pnpm db:migrate` | 生成并应用迁移 |
| `pnpm db:reset` | 清库并重放全部迁移 |
| `pnpm db:verify` | 跑 `scripts/verify-constraints.sql` 断言数据库级约束 |

迁移已生成并应用，数据库级约束已用断言验证（见 `docs/进度-2026-11-03.md`）。
